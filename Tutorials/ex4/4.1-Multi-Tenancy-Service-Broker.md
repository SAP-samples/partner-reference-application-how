# Enable API Access to SAP BTP Applications Using a Service Broker

In the multi-tenant setup, the OData services that the UI is based on are not directly accessible. To enable access to application OData services, you use a service broker with tenant-specific credentials. This broker issues OAuth2 client credentials that are specific to the application tenant and APIs that ensure tenant isolation. The OAuth2 client credentials can be used for inbound API integration scenarios, enabling integration between your SAP BTP application and third-party applications, as well as with SAP Build solutions.

### Add API-Specific Authorizations

If you need different access authorizations for APIs, such as full access with all authorizations like `PoetrySlamManagerRoleCollection` and read-only access for other integrations, introduce a new scope: 

1. Add a read-only scope to [xs-security.json](../../../ServiceBroker/xs-security.json) and add an entry to the **scopes** list:
    ```json
    {
      "name": "$XSAPPNAME.PoetrySlamReadonly",
      "description": "Read-only access to Poetry Slams"
    }
    ```

2. Add the scope to the authorization annotations in [poetrySlamsServiceAuthorizations.cds](../../../ServiceBroker/srv/poetryslam/poetrySlamServiceAuthorizations.cds):
   1. Add the scope to the **requires** list of the service.
      ```cds
      annotate PoetrySlamService with @(requires: [
        'PoetrySlamFull', // Full authorization for managers
        'PoetrySlamRestricted', // Restricted access for visitors
        'PoetrySlamReadonly' // Read-only access for APIs
      ]);
      ```
   2. Add the scope with the correct restriction to the entities `PoetrySlams`, `Visitors`, and `Visits`.
      ```cds
      {
        // Read-only access
        grant: ['READ'],
        to   : 'PoetrySlamReadonly'
      }
      ```

### Add a Service Broker to Your SAP BTP Applications

1. Ensure that the line below is available in the [xs-security.json](../../../ServiceBroker/xs-security.json) file.
    > Note: This line prevents technical internal scopes from being exposed through the service broker.
   ```json
   "authorities-inheritance": false
   ```

2. Create a service broker Node.js application:
   1. Create a new directory called `broker` in the project root folder.
   2. Run the `npm init` command in the new folder to initialize the Node.js project.
      > Note: You're prompted to answer several questions. You can use the `psmbroker` value as a package name and `Service broker for the Poetry Slam Manager sample application` as a description. Use the default values for all other fields. Once completed, this command creates a [package.json](../../../ServiceBroker/broker/package.json) file in the broker directory. Now, due to this file, SAP BTP Cloud Foundry runtime identifies it as a Node.js application.

3. Adopt the newly created **package.json**:
    Remove the line specifying the value for `main` in the newly created **package.json**. You can use the [package.json](../../../ServiceBroker/broker/package.json) file as a reference.

4. Add the service broker framework:
   
   Execute the `npm install @sap/sbf` command in the **broker** folder to download the **@sap/sbf** package and add it to your service broker.
     > Note: Make sure that you execute the commands above in the [broker folder](../../../ServiceBroker/broker). This adds a dependency in your **package.json**. It also creates a **node_modules** folder and a **package-lock.json**.

5. Add the service broker start script:
    
    Edit the [package.json](../../../ServiceBroker/broker/package.json) file of the **broker** folder and add the start command in the **scripts** section.
    ```json
    "scripts": {
      "start": "start-broker"
    }
    ```

6. Create the service catalog:
   1. Create a file called [catalog.json](../../../ServiceBroker/broker/catalog.json) in the **broker** directory and describe the service catalog.
      > Note: The service catalog describes the services offered by this service broker. It's defined in a JSON format as described in the [SAP BTP Cloud Foundry runtime documentation](https://github.com/cloudfoundry/servicebroker/master/spec.md#catalog-management).

      > Note: The Partner Reference Application defines 3 different plans. Plans define different authorization scopes, as shown in the `mta.yaml` file below.
    Here's an example of the `catalog.json`:
      ```json
      {
        "services": [
          {
            "name": "psm-servicebroker",
            "description": "PSM service broker",
            "bindable": true,
            "plans": [
              {
                "name": "fullaccess",
                "description": "Full Access plan"
              },
              {
                "name": "readonlyaccess",
                "description": "Read-only Access plan"
              },
              {
                "name": "namedaccess",
                "description": "Access plan for named users"
              }
            ]
          }
        ]
      }
      ```
   2. Execute the `npx gen-catalog-ids` command to generate unique IDs for the services and their plans in the **catalog.json** file.
   3. After ID generation, your **catalog.json** file looks like the sample [catalog.json](../../../ServiceBrokers/broker/catalog.json) file.
   4. You can now delete the **node_modules** folder and the **package-lock.json** in the **broker** folder.
   5. Run `npm install` in the **broker** folder.

7. Reuse the SAP Authorization and Trust Management service instance previously created (nothing to do here).
   - The service broker can use different services to generate and store credentials that are needed later on by applications to access your reusable service. In this example, the existing SAP Authorization and Trust Management service (_XSUAA service_) is used as a credentials provider.
   - An SAP Authorization and Trust Management service (_XSUAA service_) instance with _service-plan: broker_ is already configured to be created using the configuration in the [mta.yaml](../../../ServiceBroker/mta.yaml) project deployment descriptor file.

8. Generate a secure broker password (there is nothing to do here).
   - Later, you create instances of the service broker service per consumer tenant. To do so, you need to authenticate the consumer instance against the provider instance with credentials that you define in the provider.
   - Executing the `npx hash-broker-password -b` command would generate a random password hash that you use as specified credentials. However, this approach would store the credentials in the **mta.yaml** file in the next step. Instead, we use the credentials that are automatically generated during deployment.

9. Create a service broker application manifest:
    
    Add the `poetry-slams-servicebroker` module to the modules section in the [mta.yaml](../../../ServiceBroker/mta.yaml) deployment descriptor file.

    Here's a sample configuration:
      ```yml
      # The service broker for the poetry slam manager
      # Directly exposes the poetry slam service
      - name: poetry-slams-servicebroker
        type: nodejs
        path: broker
        parameters:
          disk-quota: 1024M
          memory: 128M
          health-check-timeout: 180
        requires:
          - name: poetry-slams-auth
          - name: poetry-slams-srv-api
        build-parameters:
          builder: npm
        properties:
          SBF_CATALOG_SUFFIX: ${space}  # Make the service broker unique in the deployed space
          SBF_ENABLE_AUDITLOG: false
          SBF_BROKER_CREDENTIALS: '{ "${generated-user}": "${generated-password}" }'    # use a random password that is generated during deployment (note that this changes the password with every deplyoment)
          SBF_SERVICE_CONFIG:
            psm-servicebroker:
              extend_xssecurity:
                per_plan:
                  fullaccess:
                    authorities:
                      - "$XSMASTERAPPNAME.PoetrySlamFull"
                  readonlyaccess:
                    authorities:
                      - "$XSMASTERAPPNAME.PoetrySlamReadonly"
                  namedaccess:
                    authorities:
              extend_credentials:
                shared:
                  endpoints:
                    psm-servicebroker: "~{poetry-slams-srv-api/srv-url}" # Tenant-specific OData endpoint for remote integrations
      ```

    - The additional service configuration (`SBF_SERVICE_CONFIG`) is a JSON object that provides additional deploy-time configuration. Usually, you use this for configurations that aren't known in advance, such as URLs. 
    - Each key in this object matches a service name in the [catalog.json](../../../ServiceBroker/broker/catalog.json) file. In the Partner Reference Application, this is **psm-servicebroker**.
      Its value is an object with the following properties:
        - `extend_xssecurity`: an object that contains the `per_plan` property. It consists of objects for each plan as defined in the [catalog.json](../../../ServiceBroker/broker/catalog.json) file. The Partner Reference Application has the plans `fullaccess` and `readonlyaccess` for **technical-user access**. The object for each plan contains the `authorities` property, which includes values that match the scope as defined in the [xs-security.json](../../../ServiceBroker/xs-security.json) file. In addition, the `namedaccess` plan has no authorities. It's used for **named-user access** to make sure that the authorization scopes are the ones of the user that is logged in. You can find more information on how to use technical and named users in the next section.
        - `extend_credentials`: An object that contains the `shared` property. It consists of an object where service end points are defined. The `psm-servicebroker` service name matches the name of the service in the [catalog.json](../../../ServiceBroker/broker/catalog.json) file.

10. To test with named users, you need an authorization code. For this code, you need a `callback url`. 

    For the tests that are provided in the next chapter, `http://localhost` is used as a `callback url`. You must declare this to the authorization service to ensure that this service accepts the corresponding authorization request. For this purpose, add the `callback url` to the `poetry-slams-auth` resource in the [mta.yaml](../../../ServiceBroker/mta.yaml) file.

    Here is the corresponding addition:
    ```yml
    resources:
      - name: poetry-slams-auth
        parameters:
          config:
            oauth2-configuration:
              redirect-uris:
                - http://localhost # Redirect for local testing with the service broker
    ```

11. [Build and deploy the multi-tenant application to the provider SAP BTP subaccount (sync point 2 and 3)](../../README.md).

In the next step, you create an instance of the service broker in a consumer subaccount and use it to access the OData service of the application. Go ahead with [Configure and Consume the APIs of the SAP BTP Application](./4.2-Multi-Tenancy-Provisioning-Service-Broker.md).
